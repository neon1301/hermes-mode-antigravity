# 🚀 7-Phase Feature Development Protocol (`/hermes feature`)

Протокол разработки фич и крупных изменений, адаптированный из `anthropics/claude-plugins-official` (`feature-dev`) под стандарты Hermes Fleet Enterprise.

---

## ⚡ Fast-Path для тривиальных правок
Если задача представляет собой тривиальную правку (исправление опечатки, изменение комментария, правка 1–5 строк без изменения интерфейсов/контрактов):
- **Фазы 1–4 пропускаются.**
- Оркестратор сразу переходит к **Фазе 5 (Реализация)** с обязательным прохождением Build Gate (`npm test` / компиляция) и Token Economy Gate (`ask_question`).

---

## 🏛️ 7 Фаз разработки крупных фич

### Фаза 1: Discovery (Исследование проблемы и границ)
- Формулировка бизнес-цели и проблемы с точки зрения пользователя.
- Фиксация **Goals** (что входит в фичу) и **Non-Goals** (что явно исключено из скоупа текущей задачи).
- Формирование атомарного чеклиста `REQ-1..REQ-N`.

### Фаза 2: Codebase Exploration (Анализ кодовой базы)
- Поиск всех зависимых компонентов через `grep_search` и `find_by_name`.
- Построение цепочки вызовов и определение затронутых слоёв (UI ➔ Backend ➔ DB ➔ Protocol).
- Проверка правила `N из N`: фиксация всех однотипных мест в проекте, требующих синхронного обновления.

### Фаза 3: Clarifying Questions (Уточняющие вопросы)
- Если требования допускают неоднозначность или есть развилка в логике:
  - Вызовите инструмент **`ask_question`** с чёткими вариантами выбора (`options`).
  - Запрещено додумывать пользовательские предпочтения в критических архитектурных развилках.

### Фаза 4: Architecture Design (3 Альтернативы архитектуры)
Перед написанием кода оркестратор представляет пользователю 3 альтернативных варианта реализации:
1. **Минимальные правки (Minimal Changes):** Локальное точечное решение задачи в существующих файлах с наименьшим диффом.
2. **Чистая архитектура (Clean Architecture):** Полная декомпозиция, выделение новых интерфейсов/DTO, изоляция слоёв (под ревизией `@stanislav`).
3. **Прагматичный баланс (Pragmatic Balance) [Рекомендуемый]:** Оптимальное соотношение скорости, расширяемости и сохранения стабильности без оверинжиниринга.

### Фаза 5: Implementation & Capability-Routed Waves (Реализация)
- Правка 1–3 файлов: Lead выполняет точечно через `edit_file` / `write_file`.
- Правка 4+ файлов: Запуск рабочих субагентов (`define_subagent`, `self`) в изолированных непересекающихся волнах по 3–5 файлов.
- Железный закон TDD: сначала падающий тест (reproducer), затем имплементация.
- Соблюдение правил флота: Zero-Hardcode (Правило 9), запрет патч-скриптов (Правило 8).

### Фаза 6: Quality Review & High-Confidence Filtering (Аудит качества)
- Профильное ревью кода силами специализированных экспертов:
  - **`@viktor`:** PR Test Analyzer + Security Audit (L2 Diff-Review).
  - **`@dmitry`:** Type Design Analyzer (инварианты и типы).
  - **`@anna`:** Comment Analyzer (актуальность документации и комментариев).
  - **`@kritik`:** UX & Layout Review (при правке окон и UI).
- **Фильтр уверенности (Confidence Filter):**
  - Для общих замечаний по стилю, рефакторингу и чистоте кода в отчёт включаются замечания только с **`confidence >= 80%`** (отсечение субъективного шума).
  - **Исключение:** Замечания по безопасности (`high` / `critical`) и утечкам секретов репортятся **ВСЕГДА**, независимо от порога уверенности!

### Фаза 7: Summary & Verification Receipts (Итоги и квитанции)
- Запуск полного набора локальных тестов через `verify.ps1` / `verify.sh` / `npm test`.
- Формирование итогового отчёта с путями к изменённым файлам (`file:///...`), номерами строк и доказательствами прохождения тестов.
- Обновление чекпоинта `.hermes/checkpoint.md`.
