# 📐 Адаптивное планирование Lead Orchestrator (BMAD Methodology)

Методология адаптивного планирования оркестратора Hermes Fleet, интегрированная на базе мировых практик BMAD (`bmad-code-org/BMAD-METHOD`). Регламентирует шкалу глубины планирования, журнал архитектурных решений/допущений и закон спецификаций Spec Law «Done when».

---

## 🧗 1. Шкала глубины планирования (Scale-Adaptive Planning Ladder)

Оркестратор Hermes выбирает уровень церемонии планирования строго по сложности задачи, предотвращая оверинжиниринг мелких фиксов и неполноту сложных доработок:

### Уровень 1: Micro / Fast-Path
* **Критерии применения:** Точечные правки (1–2 файла, исправление опечатки, корректировка константы, добавление флага, устранение очевидного бага).
* **Глубина церемонии:** Минимальная. Lead формулирует 1–2 пункта `REQ`, не вызывает субагентов на аудит, вносит правку через `edit_file`, прогоняет локальные тесты (`Single Build Gate`) и запрашивает у пользователя подтверждение по экономии токенов (`ask_question`).
* **Артефакты:** Запись в чате, без создания промежуточных ADR.

### Уровень 2: Standard / Feature
* **Критерии применения:** Новая функциональность среднего масштаба (3–10 файлов, добавление эндпоинта, новый UI-компонент, миграция БД, интеграция сокета).
* **Глубина церемонии:** Стандартный 7-фазный цикл. Обязательный реестр `REQ-1..REQ-N`, привлечение 2–3 профильных специалистов Контура A (например, `@dmitry` + `@elena` + `@viktor`), формирование Patch Blueprint, 1–2 волны записи Контура B, верификация через `Single Build Gate`.
* **Артефакты:** Реестр `REQ-1..REQ-N`, `.hermes/checkpoint.md`, канбан-доска.

### Уровень 3: Complex / Enterprise
* **Критерии применения:** Изменение макро-архитектуры (>10 файлов, смена движка хранения, протокольные изменения оборудования, интеграция с SAP, рефакторинг монолита).
* **Глубина церемонии:** Максимальная строгость.
  1. Discovery & Repo Map (`skills/hermes/references/repo-map-protocol.md`).
  2. Анализ 3 архитектурных альтернатив с оценкой рисков и оценкой ставок (Stakes Evaluation).
  3. Оформление архитектурного решения в `.hermes/decisions.md` и `docs/adr/ADR-NNNN.md`.
  4. Формирование графа задач в `.hermes/tasks.json` с явными `blocked_by`.
  5. Поэтапные волны по 3–5 воркеров в изолированных воркспейсах с дисциплиной Merge Queue (Refinery).
  6. Тройной барьер приёмки: Stanislav (`[COMPLIANCE PASS]`) + Viktor (`[QA PASS]`, `[SECURITY PASS]`) + Kritik (`[UX PASS]`).

## 📓 2. Журнал решений и допущений (`.hermes/decisions.md`)

Для переноса контекста между спринтами и сессиями Lead ведёт журнал `.hermes/decisions.md`, где каждое ключевое допущение фиксируется с указанием уровня ставок (Stakes Ladder):

### Формат записи в `.hermes/decisions.md`:

```markdown
### [DEC-NNN] <Краткое название решения>
- **Дата:** <ISO-8601>
- **Статус:** PROPOSED | ACCEPTED | SUPERSEDED | REJECTED
- **Уровень ставок (Stakes):** 
  - `HIGH`: затрагивает системные границы, схемы БД в проде, протоколы физических станков или риск потери данных.
  - `MEDIUM`: межмодульные контракты, выбор библиотеки, структура DTO.
  - `LOW`: локальная стилизация, внутренняя структура приватного метода (легко обратимо).
- **Допущения (`[ASSUMPTION]`):**
  - [ASSUMPTION] <Формулировка гипотезы> | Проверка: <Как и кем будет проверено> | Статус: [ПРОВЕРЕНО] / [ОПРОВЕРГНУТО]
- **Решение:** <Принятый вариант с обоснованием отказа от альтернатив>
- **Последствия:** <Влияние на смежные модули и зависимости>
```

### Интеграция с жизненным циклом сессии:
- При выполнении `/hermes save` файл `.hermes/decisions.md` фиксируется вместе с `.hermes/checkpoint.md` и `.hermes/tasks.json`.
- При старте нового чата и вызове `/hermes resume` активные решения и неподтверждённые допущения со статусом `HIGH` поднимаются в контекст Lead Orchestrator.

## 📜 3. Закон спецификаций Spec Law «Done when»

Каждое требование в реестре `[REQ-1..REQ-N]` обязано содержать явный, объективно проверяемый критерий приёмки **«Done when»**:

### Принципы Spec Law:
1. **Тестируемость / Демонстрируемость:** Критерий сдачи формулируется как воспроизводимый проверочный факт:
   * Команда завершилась с кодом 0 (например, `npm test` завершился с 299/299 PASS).
   * Файл существует на диске и его размер укладывается в бюджет (например, `fleet-protocol.md <= 12288 байт`).
   * Строка вывода или API-ответ строго соответствует регексу/сигнатуре.
2. **Запрет субъективных формулировок:** Категорически запрещены критерии вида:
   * ❌ *«Код стал чище и понятнее»*
   * ❌ *«Улучшена производительность»* (без указания бенчмарка в мс или МБ)
   * ❌ *«Интерфейс выглядит красивее»* (без указания токенов, шрифтов и вердикта `[UX PASS]`)
3. **Автоматический отказ при отсутствии «Done when»:** Если требование сформулировано без проверяемого условия сдачи, Lead возвращает задачу на доработку формулировки до передачи субагентам.
